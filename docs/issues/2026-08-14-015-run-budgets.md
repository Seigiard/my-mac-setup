# Run budgets exist for flows and not for pipelines, and nothing caps a wasted run

## Why this exists

Three cost mechanisms exist in this system and they do not add up to a budget.

**`se flow --budget N`** is a run ceiling. `evaluateBudget` (`home/private_dot_claude/dot_smithers/workflows/lib/cost.ts:161`) compares measured spend against it, and a breach PARKS the run for an operator acknowledgement — KTD9 is explicit that it must never hard-kill. It applies to composed flow specs only.

**`se pipeline` has no budget flag at all.** The pipeline's only money knob is `workBudgetUsd`, an input with a default of $50, documented in its own schema as "Runaway circuit breaker for the work leg, NOT a cost target" (`home/private_dot_claude/dot_smithers/workflows/se-pipeline.tsx:76`). It is not exposed on the launcher, it covers one stage of five, and it is a breaker rather than a ceiling. So the command most runs are launched with cannot be given a spending limit.

**`agentCapUsd`** is a per-leg hard kill derived from a block's cost profile, deliberately decoupled from the run ceiling. The comment above it records why: wiring the ceiling into the cap made every leg hard-kill exactly where KTD9 says to park, and a run launched without `--budget` passed a cap of $0, which killed any agent leg on its first token.

The gap shows up in real spend. Recorded runs, from `se list`:

```
green | fixture-reverse-plan.md                     |  2.72
green | fixture-reverse-plan.md                     |  1.53
green | 2026-08-13-001-test-link-doc-link-href      |  4.65
green | 2026-08-12-001-fix-vrt-walkback-inherited   | 17.35
green | 2026-08-12-001-fix-console-select-raw       |  7.39
stopped-after-second-failure:work | 2026-08-12-002  |  5.43
stopped-after-second-failure:work | 2026-07-23-001  | 10.65
```

The last two are the point: $16 spent across two runs that stopped at the work stage without shipping. Nothing warned before the spend, and nothing capped it. Today's failures were cheaper only by luck — `run-1786717826270` parked after one work leg because the KTD14 tree-hash invariant fired, not because a budget did.

Cost visibility is also asymmetric. KTD6 says tokens are the metric and USD an estimate, and the run summary reports both — after the run. Before the run there is no estimate at all, so the operator authorises an unknown amount.

## Scope

A design decision spanning:

- `home/private_dot_claude/dot_smithers/bin/executable_se` — `pipeline` has no `--budget`; `flow` does.
- `home/private_dot_claude/dot_smithers/workflows/se-pipeline.tsx` — `workBudgetUsd`, and where a whole-run ceiling would be evaluated.
- `home/private_dot_claude/dot_smithers/workflows/lib/cost.ts` — `evaluateBudget`, `agentCapUsd`, and the usage reader that measures spend.

## Open decisions

- **Whether `se pipeline` gets a run ceiling, and whether it defaults to something.** A ceiling nobody sets protects nobody; a default that is too low parks healthy runs and trains the operator to acknowledge without reading. The observed distribution ($1.50 fixture to $17 real) means one default cannot serve both.
- **What the ceiling is scoped to.** Whole run, or per stage. A whole-run ceiling is what an operator thinks in. A per-stage one catches a runaway leg earlier, which is where the money actually goes.
- **What a breach does at each point in the run.** KTD9 says park. Parking after the work leg has already been paid for is a notification, not a control. Parking *before* dispatching an expensive leg — checking projected spend against the remaining ceiling — is a control, and needs a per-block cost estimate to exist.
- **Whether a pre-launch estimate is worth building.** The block catalogue already carries cost profiles, and `se pipeline --dry-run` could print an expected range before the operator commits. It would be an estimate over an estimate, and wrong sometimes; the alternative is authorising with no number at all.
- **Whether a failed run should be cheaper by design.** The two `stopped-after-second-failure:work` runs each paid for two work legs before stopping. Whether a second attempt is worth its cost, and whether that should be a budget decision rather than a fixed retry policy, is unsettled.
- **How this interacts with the pre-flight refusals.** `docs/issues/2026-08-14-013-fresh-worktree-has-no-dependencies.md` moved one class of failure to before any spend. Every failure class moved earlier reduces what a budget has to catch, so the two efforts trade against each other and the budget work should follow, not precede, the cheap preflight checks.

## Resolution

The Smithers pipeline and flow budget machinery were removed, so a pipeline run budget is no longer applicable.
