## Why this exists

PR #135 (fix/pi-updater-failure-notifications, a Pi TypeScript extension change with no herdr-child involvement) hit a single test-ubuntu failure on its first CI attempt: tests/bashunit/scripts_test.sh test 040, 'herdr-child superseded watcher cannot publish failure metadata over a new generation' (274 passed, 1 failed, 1185/1186 assertions). Failing attempt: https://github.com/Seigiard/my-mac-setup/actions/runs/33640164802/job/100281371063 (run 33640164802, attempt 1, test-ubuntu, conclusion failure). Four independent signals say flake rather than regression: (1) test-macos passed in the same run, exercising the same suite -- https://github.com/Seigiard/my-mac-setup/actions/runs/33640164802/job/100284544665; (2) lint passed in the same run -- https://github.com/Seigiard/my-mac-setup/actions/runs/33640164802/job/100284593086; (3) PRs #134 and #136 both passed test-ubuntu from the same main base at the same time (independently confirmed via gh pr view: both show test-ubuntu SUCCESS); (4) rerunning the identical commit's test-ubuntu job passed in 4m25s -- https://github.com/Seigiard/my-mac-setup/actions/runs/33640164802/job/100284541716 (attempt 2, conclusion success). The diff under test in PR #135 touched only the Pi TypeScript brew-auto-update extension, its tests, and docs/issues entries -- nothing in the herdr-child supervision path that test 040 exercises, which rules out a code-caused regression from that PR. Test 040 is the deterministic barrier regression test added to guard a real, already-fixed concurrency window (the record that requested it, 2026-08-30-001, was removed from docs/issues/ in 13402c1 together with 72 other closed records; the surviving write-up of this family is docs/solutions/design-patterns/idle-machine-wall-clock-bounds-are-latent-flakes.md): a superseded watcher restoring stale failure metadata over a newer generation's cleared state. A flaky guard erodes trust in exactly the coverage that fix bought -- a real regression in that window could hide behind 'it's just flaky.' Compared against the closed reap-close-race flake record (2026-08-29-004, also removed in 13402c1): that issue was a different test ('herdr-child reap invalidates before close while spontaneous loss wakes the parent') guarding a different mechanism -- an implicit, unbounded scheduling race between the watcher's supervision deadline and reap-before-close ordering, with no synchronization barrier; it was fixed by widening that test's deadline to 600000ms so the timeout branch could never fire mid-reap. Test 040's scenario is structurally different: it already uses an explicit deterministic barrier (HERDR_CHILD_TEST_FAILURE_PUBLISH_BARRIER, child_wait_for_file, an explicit release file) to synchronize the takeover interleaving it proves, rather than relying on real-world scheduling latency. The two issues are both in the herdr-child watcher / CPU-load-sensitive family, worth cross-referencing, but this is a distinct root cause, not a recurrence of 2026-08-29-004 -- filing new rather than reopening or extending that closed issue.

Reproduce under artificial CPU load (busy loop pinning cores while looping the single test, matching the method the closed reap-close-race record (2026-08-29-004) used) to identify which specific bounded wait inside the test is timing-sensitive -- candidates include the up-to-500-iteration/0.01s polling loops that wait for watcher_pid or new_watcher_pid to die, and the child_wait_for_log / child_wait_for_file calls around the barrier release. ## Resolution

Not reproducible as filed. All runs below are macOS (Darwin 23.6.0, host bashunit), not the Ubuntu container the original failure came from; that platform gap is the main limit on this close, since the CI failure was a test-ubuntu job. Test 040 ran 87 times under load on macOS without one failure: 40 focused iterations at 16 busy loops, 40 focused at 48 busy loops, and 7 full parallel suite runs (bashunit -j 8) at 12 busy loops. The Scope asked for a reproduction that would identify the load-sensitive wait; no reproduction appeared, so widening any specific wait inside test 040 would be a change with no observed failure behind it.

One real observation did come out of the loaded suite runs, in the same family but a different test. Test 046 ('herdr child failed reap restores supervision') failed once in those 7 suite runs, timing out inside child_wait_for_file (tests/bashunit/scripts_test.sh:2584) while waiting for parent-prompt-accepted. That helper polls 500 times at 0.01s, a fixed 5-second wall-clock bound and the exact shape described in docs/solutions/design-patterns/idle-machine-wall-clock-bounds-are-latent-flakes.md. Test 046 then passed 40 of 40 focused iterations at 48 busy loops, so the trigger is contention between concurrent suite processes rather than raw CPU starvation. Because child_wait_for_file is shared, that same bound sits underneath test 040's own barrier waits, which is the most plausible mechanism for the original CI failure even though it could not be pinned to test 040 by measurement.

Whether the sweep itself changed the flake rate was not established. At the observed rate of roughly one failure in seven suite runs, a five-run control on the pre-sweep commit would have been consistent with any rate, so no control was run rather than producing a number that would read as evidence.

Two issue-file paths cited in the body were dead (both records removed in 13402c1) and were replaced with the surviving pattern document.
