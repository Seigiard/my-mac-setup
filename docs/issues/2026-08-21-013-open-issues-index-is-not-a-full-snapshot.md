## Why this exists

`docs/issues/_open-issues.md` presents itself as a snapshot generated by
`rg -l 'status: open|status: in-progress' docs/issues`, but it has repeatedly
failed to match that command's output. When this issue was filed the tables
listed 40 issues against 54 matched files; on `main` at `5672305` the same gap
was eleven — 45 open issue files against 34 rows. The drift is chronic, not a
one-off.

The failure is quiet, which is what makes it worth a file. An index that is
merely incomplete still reads as authoritative, so someone checking "is this
already filed?" against it gets a wrong answer and files a duplicate.

**Regenerated 2026-08-21.** The index now lists all 53 open issues, one stale row
(`2026-08-20-002-coordinator-location-test-flake.md`, closed) was removed, and
nine unlisted issues were placed into severity groups. That fixes the current
enumeration. It does not fix the mechanism: every drift so far has come from
filing an issue and not adding its row, a step no tooling enforces, so the same
gap reopens with the next issue filed.

## Scope

What remains is the mechanism, not the enumeration:

- Decide whether this file should be generated rather than hand-maintained.
  `CLAUDE.md` already tells contributors to list open issues with
  `rg -l 'status: open' docs/issues`, so the index earns its keep only through
  the grouping and severity judgment the raw command cannot supply.
- If it stays hand-maintained, add something that makes an unlisted open issue
  red — a test comparing the `rg` output against the file's links is the cheap
  version.

## Open decisions

- Whether to keep a hand-maintained grouped index at all, or replace it with a
  generated list plus a short hand-written "what matters now" section. The
  grouping is the part with real value; the enumeration is the part that rots.
