# Document Navigation Interception - Research

## Findings and boundary

**Claude mods and Pi tool overrides can answer a read with a successful TOC without executing the original reader.** Result-rewrite events alone only replace context after execution. Attached PDFs remain a separate, partly unverified route.

This is source research, not a deployed adapter or a runtime demonstration. Evidence was collected on 2026-10-07. Only this note was added. No client, mod, configuration, version, or issue was changed. No sessions, builds, or tests were started.

The supplied scope of [#409](https://github.com/Seigiard/my-mac-setup/issues/409) remains the baseline: OpenCode first; first PDF read returns a TOC; repeat read is allowed; a PDF TOC can refer to verified Markdown and its TOC; no OCR in the hook; short-budget fail-open behavior; attachments out of scope. The issue was not queried or edited. Opportunities below are research proposals, not additions to that scope.

Evidence labels:

- **Supported**: an explicit primary-source contract or inspected implementation. This does not mean demonstrated on this machine.
- **Proposed**: a design derived from those contracts, not implemented here.
- **Uncertain**: missing evidence, version mismatch, or a behavior that needs a runtime observation.

## Claude: the exact interception contract

### Successful replacement versus denial

Registration is `export function register(on, options)`, followed by `on(eventName, matcher?, handler)`. A normal handler receives `($, e, next)`; `tool.call` arguments are spread onto `e`, not nested in `e.input`. For `Read`, the pinned types declare `file_path: string`, `offset?: number`, `limit?: number`, and `pages?: string`. PDF `pages` describes a maximum of 20 pages per request. `tool.check`, in contrast, uses `e.input`. [C2; C4 lines 12479–12487]

The important contract is `ToolCallResult`, not a generic string example:

> “Core validates a hook's answer against the tool's output schema when it has one, maps it for the model with the tool's own mapper, and records it in the transcript as the tool's result.” [C4 lines 9844–9852]

- `{ deny: reason }` is an **error result**. It is not a clean TOC response.
- `{ result: ... }` without `next` answers successfully and skips later handlers and the built-in reader. No permission prompt is needed for an execution that never happens.
- Core results can include `ref`, `text`, and `isError: true`. These are not fields to fabricate for a successful replacement. Returning the original result unchanged preserves core's messages.
- Invalid results fail the hook; absent a custom catch handler, the chain fails open. An invalid synthetic `Read` result can therefore cause the real read to proceed. [C2; C4 lines 9822–9903]

**Derived API fragment; high confidence for the pinned type snapshot, not runtime-validated.** This is the return branch inside `on('tool.call', { tool: 'Read' }, ...)`. `tocText` and `tocPath` are already available values, not invented API functions:

```ts
return {
  result: {
    type: "text",
    file: {
      filePath: tocPath,
      content: tocText,
      numLines: tocText.split("\n").length,
      startLine: 1,
      totalLines: tocText.split("\n").length,
    },
  },
};
```

This follows `BuiltinToolResults.Read`'s text branch [C4 lines 12914–12929]. It does not call `next`, `$.fs`, or a process. It demonstrates **no original-reader I/O**, not a complete index acquisition strategy. Name the synthetic TOC and its line domain honestly; do not present TOC line counts as PDF page counts. The mapper's handling of a text result for a PDF request still needs a runtime observation. A bare `{ result: 'TOC' }` from a generic tutorial is not sufficient evidence for built-in `Read`.

### Continuation, ordering, and failure

`next(e)` is the remaining middleware chain, not an `original()` handle that bypasses other mods. It runs downstream handlers and finally core. Each invocation runs that chain again; retries can execute the tool again. A handler must return the continuation result or a valid replacement. `e` is deeply frozen, so rewrites use a copied object. `tool`, `tool_use_id`, and `agentId` are reserved. [C2; C4 lines 5217–5236, 9789–9797]

The first handler is outermost: before-work runs in chain order; after-work unwinds in reverse. The documented tiers are the managed guard/prepend/other managed mods, user mods, managed append mods, then other built-ins. User manifest dependencies and registration order further order handlers. `sec-default` is conditional on organizational/managed context; a managed `prependPlugins` list controls its placement. It is not accurate to say it is always first in every personal session. [C2, C3]

Managed `PreToolUse` hooks run before any mod `tool.call`; a block there is final and the mod never sees the call. Other settings/plugin `PreToolUse` hooks run at the core end, after the last `next`. A synthetic answer skips them. `tool.check` runs after permission rules and those hooks. This is a compatibility consideration for a navigation adapter, even though the TOC response itself executes no read. [C2]

Handlers can await. `next.signal` reports abandonment. The default own-execution budget is 10 seconds; time inside `next` and most `$` calls does not count. `$.clock.sleep` does count; `$.process.run` has its own default 30-second timeout. These defaults do **not** provide #409's short end-to-end budget. Before-`next` failures skip the handler; after-`next` failures preserve the downstream result without repeating execution. [C2, C3]

### State, session boundaries, and concurrency

Module variables last until reload; `register` and `session.start` run again after reload. `session.start` does not run after `/clear`, `/resume`, or `/branch`. `session.end` does, and `/branch` reports `resume`. `$.state` survives reload but resets at those session boundaries; `$.store` is shared persistent storage across sessions on the machine. A store get/set pair is not atomic. [C3; C7, “Keep state”]

`$.session.id()` supplies session identity. `tool_use_id` identifies a call; optional `agentId` identifies a subagent loop. `turn.start`, `turn.step`, and `turn.complete` carry `turnId`; the pinned `tool.call` shape does not provide that field. `prompt.submit.turnId`, when present, identifies the already-running turn over which input arrived, not necessarily a newly submitted turn. Mods see subagent tool calls, but a single unkeyed module variable is not per-agent state. [C2; C4 lines 164–174, 7188–7239, 9789–9797, 10368–10446]

**Proposed:** key first-read state by session and canonical document identity, with an explicit choice about whether subagents share it. Use an in-flight reservation before asynchronous index work and release it on failure. Do not infer serialization from middleware order; the sources provide no global atomic first-read guarantee. Reload, resume, compaction, and simultaneous reads need proof before calling the policy “once per session.”

### Prompts, attachments, UI, and limits of interception

`prompt.submit` can change `text`, add model-only `context`, or return `{ drop }`. The pinned types say its text has **pastes already expanded**. Its `attachments` contain only `type: 'image' | 'audio' | 'document'`, optional `mediaType`, and optional `filename`: “its kind, never its bytes.” The result contract has no attachment-bytes replacement field. Adding `context` after `await next(e)` is too late: the prompt already entered. [C4 lines 7165–7253]

`prompt.attachment` is easily misread. It handles engine-added **text** such as reminders, mentioned-file text, and hook context. The pinned contract explicitly says only attachments carrying text are raised. `{ text: null }` omits that text; it is not evidence that a PDF document block or image bytes are suppressed. Current docs add typed `detail` for some kinds, which the older public declaration lacks. [C3; C4 lines 6544–6586]

Current `prompt.mention` is a useful later addition: in `2.1.290+` it fires **before reading an @-mentioned file**, accepts `next({ ...e, path })`, or `{ deny: reason }`. This could redirect a mention to a TOC. The inspected public declarations do not include this event, so a fuller exact type or arbitrary PDF-byte replacement must not be invented. Pasted, Desktop-uploaded, SDK-provided, and @-mentioned files need separate coverage. [C3]

`ui.render` changes drawings, not tool results or stored model messages; the `UserMessage` declaration states this explicitly. `$.ui.log` is also invisible to Claude. Hiding a PDF result in the transcript does not save model context. `turn.step` exposes request metadata/model selection, not a documented general mutable message-array hook. `session.append` in current docs can rewrite stored row content, but this note does not establish pre-I/O interception or coverage of every PDF attachment route through it. [C3, C8; C4 lines 7858–7863, 10427–10446]

A `Read` matcher does not inspect file access inside Bash, an MCP service, arbitrary host internals, or another program. `$` calls are separate interceptable events only for later mods' calls through that API. Managed pre-tool blocks, upstream short circuits, and earlier tiers can prevent our handler from running. The permission prompt itself is not a replaceable render surface. [C1–C3, C8]

### Settings hooks are more capable than an old comparison may suggest

The current `PreToolUse` contract has permission decisions, `updatedInput`, and `additionalContext`, but no synthetic-success return slot. Rewriting `file_path` to an existing TOC can avoid reading the PDF, but still runs `Read` and reads the TOC file. Denial avoids the read but produces a refusal. [C9, “PreToolUse decision control”]

Current `PostToolUse` supports **`updatedToolOutput` for all tools**, not only `updatedMCPToolOutput`. The replacement must match the output schema; an invalid built-in replacement is ignored. It runs before output is sent to Claude, but after tool I/O and after original-output telemetry capture. This is context masking, not read avoidance. No introduction version was found for this field, so its presence in current docs is not a claim that local `2.1.285` was exercised. [C9, “PostToolUse decision control”]

## Pi 1.0.4: events, successful override, and active tools

### Exact contracts and execution order

Pi uses `export default function (pi: ExtensionAPI)` and `pi.on(event, handler)`. Handlers run in extension-load and registration order and can be asynchronous. The installed types and implementation establish these contracts [P2–P5]:

| API | Inputs and result | Navigation implication |
|---|---|---|
| `tool_call` | `toolName`, `toolCallId`, optional `parentToolCallId`, mutable `input`; return `{ block?, reason?, terminate? }` | Mutate arguments or block; no synthetic-success field. Mutations are not revalidated. |
| `tool_result` | Call IDs, name/input, `content`, `details`, `structuredContent?`, `isError`, usage; return optional replacements | Runs after execution, before the finalized tool-result message reaches the next model request. Later handlers see earlier changes. |
| `input` | `text`, `images?: ImageContent[]`, `source`, optional `streamingBehavior`; return `continue`, `transform` with text/images, or `handled` | Before skill/template expansion, but after extension-command dispatch. Not universally before attachment I/O. |
| `before_agent_start` | Expanded `prompt`, `images`, rendered `systemPrompt`, mutable `systemPromptOptions`; return custom `message` and/or `systemPrompt` | Adds context or changes the system prompt; no direct replacement-user-prompt return field. |
| `context` | `messages: AgentMessage[]`; return `{ messages? }` | Request-local message transformation before each LLM call; system/tool state is restored afterward. |
| `context_with_system` | Full transcript after `context` | Can transform the complete outgoing transcript; must preserve the required leading system message. |

`tool_call` block becomes `isError: true`. It takes the immediate-result branch and **skips `afterToolCall`/`tool_result`**, in both serial and parallel execution. Thus “block read, then use `tool_result` to turn the denial into success” does not work here. Executed tools, including thrown execution errors, do reach finalization. `tool_result` can replace `isError`, but that does not undo I/O. [P5 lines 375–463, 481–566, 593–632]

`tool_result` replacement occurs before `createToolResultMessage`. Raw output has already existed in the tool and may have been emitted as progress or seen by earlier handlers. Replacing `content` without `structuredContent` drops the old structured result. This prevents inconsistent structured data from surviving a text rewrite, but renderer-only changes do not alter either model payload. [P2 lines 105–148, 188–190; P4 lines 900–971; P5]

### Override the reader for successful no-read results

The installed upstream example explicitly registers `name: 'read'` to replace the built-in tool. The actual signature is:

```ts
execute(
  toolCallId: string,
  params: Static<TParams>,
  signal: AbortSignal | undefined,
  onUpdate: AgentToolUpdateCallback<TDetails> | undefined,
  ctx: ExtensionToolContext,
): Promise<AgentToolResult<TDetails>>;
```

Copied from installed `dist/core/extensions/types.d.ts:494` [P3]. A returned result requires `content` and `details`; success is the default unless `isError: true` is returned. Throwing produces an error. A field such as `details: { error: true }` is not itself an error signal. [P2 lines 132–148; P5 lines 568–586]

**Derived return fragment; high confidence from the installed implementation, not run here:**

```ts
return {
  content: [{ type: "text", text: tocText }],
  details: { navigation: "toc", sourcePath },
  structuredContent: tocText,
};
```

This can answer the original model-issued `read` in one call without executing its reader. `structuredContent: tocText` fits the built-in read's string output schema when preserving that schema. For pass-through, `createReadToolDefinition(ctx.cwd, options?)` provides the original definition and its five-argument `execute`; `createReadTool` provides the agent-core wrapper. Call the captured factory-produced implementation directly. `ctx.executeTool('read', ...)` re-enters the active named tool and is not an “original reader” escape hatch. [P6; P8]

Pi also exposes `ReadOperations` with `readFile(absolutePath): Promise<Buffer>`, `access(absolutePath): Promise<void>`, and optional image detection. That is a lower-level replacement option. An early return from an overridden `execute` is the clearer boundary for avoiding all original read operations. The native read schema has `path`, `offset`, and `limit`, **no PDF `pages` field**. Genuine PDF page tools need their own implementation. [P8]

### Session state, concurrency, and attachments

Pi's extension runtime is torn down on quit, reload, new session, resume, and fork; `session_shutdown.reason` names these. `session_start.reason` distinguishes `startup`, `reload`, `new`, `resume`, and `fork`. Tree navigation has `session_before_tree`/`session_tree`; compaction has before/success/failure events. A closure set is runtime state, not automatically durable session or branch state. [P3 lines 554–650]

For persisted branch-sensitive state, upstream recommends tool-result `details` or `pi.appendEntry()` and reconstruction through `ctx.sessionManager.getBranch()`. Rebuild after tree navigation if the policy follows the active branch; decide explicitly whether compaction retains or resets first-read state. `ctx.sessionManager.getSessionId()` gives session identity. Tool IDs are explicit; nested calls use `<parent id>/<n>`. `turn_start` exposes `turnIndex` and `timestamp`, not Claude's `turnId`. Parallel tools can race; reserve per-document state before awaiting TOC acquisition or use the documented sequential execution mode. [P2 lines 123–148, 222–234; P3 lines 789–802, 896–905]

The `input` event can replace attached **images** as well as text. `before_agent_start` sees expanded input; `context` can replace outgoing messages. None supplies a documented generic PDF attachment record with a filesystem path and raw PDF bytes. CLI `@file` processing has already called `access`, `stat`, MIME detection, and `readFile` before it returns text/images for the prompt. Non-image files take a UTF-8 text path, not a native PDF page pipeline. Transforming that prompt cannot recover avoided I/O. Other UI/provider attachment routes need separate proof. [P3 lines 701–710, 873–895; P7]

The repository also installs `pi-subagents`; this research does not establish that another process launched by that extension shares the parent's navigation state. Pi tool-event coverage in one runtime must not be generalized to every external subagent. [R3]

### Verified interaction with pi-codex-conversion

The managed package list includes `npm:@howaboua/pi-codex-conversion`. The installed package is **3.0.42**. Its activation code calls `pi.setActiveTools`; `mergeAdapterTools` removes default `read`, `bash`, `edit`, and `write` from the active list, then supplies adapter tools. Core adapter names include `exec_command`, `write_stdin`, and `apply_patch`; code mode uses `exec`/`wait`. [R3; P9]

Consequently, overriding Pi's built-in `read` is not sufficient evidence for coverage of this user's active toolset. When this conversion mode is active, shell reads or code-mode paths may never invoke that name. Mode selection and actual active tools were not inspected in a live session. Integrating with conversion or exposing a dedicated navigation tool is a separate decision; do not silently reactivate `read` and change the user's toolset. [P9]

## Consequences for our PDF/Markdown work

1. **Clean TOC results are a real improvement opportunity.** Claude `tool.call` and Pi `read` overrides provide the success channel that current denial adapters lack. This changes transport options, not #409's OpenCode-first priority.
2. **Page tools are possible, not supplied by these events.** Claude can register `$.tool.register({ name, description, inputSchema })` at `session.start` and handle `mcp__<plugin>__<name>` with `tool.call`; Pi uses `pi.registerTool`. Claude already has native `Read.pages`. Pi needs a PDF reader behind any new page API. Extraction, rendering, source-page identity, and verified Markdown references remain separate responsibilities. [C8; P8]
3. **Keep attachment work separate.** Claude `prompt.mention` improves the @-file route on newer builds. It does not establish universal upload interception. Pi input/context transformations improve model-context control but do not guarantee pre-read interception. These are proposed follow-ups outside accepted scope.
4. **Retain the pure-policy boundary.** The current shared `Policy.evaluate` is “Pure, synchronous, bounded — no I/O”; current decisions are only allow/block/context, and the canonical tool union has no read kind. Keep matching and decision logic pure. Put index lookup, freshness verification, session state, cancellation, and deadlines in an adapter/service layer. A future successful-result outcome must be explicit rather than encoded as a denial. [R2]
5. **Shared logic needs packaging work for Claude.** Mods cannot import Node APIs or dynamically import the deployed `~/.local/lib/agent-hooks` module as the existing adapters do. Static relative imports must stay inside the plugin, with the special `claude-code` import allowed. Pure JavaScript policy code can be shared through a deliberate build/package boundary; I/O goes through `$`. The tutorial's “sandbox” describes the JavaScript environment, not an OS security boundary: `$` still acts with the user's permissions. [C1, C5, C8]
6. **Fail open under a real short budget.** Cache/sidecar failure must delegate once to the original reader. Reading or validating an index is still I/O even when original PDF extraction is avoided. Claude's 10-second hook budget excludes most host calls; Pi `tool_call` exceptions block by default. Neither behavior implements our fail-open latency policy automatically. OCR and whole-book conversion remain outside the interception path. [C3; P2 lines 258–263; R2]

### Runtime proof still needed before implementation claims

- On an authorized supported Claude build, generate its types and observe a schema-valid synthetic `Read` result: success status, TOC text seen by the model, no original file read, honest source metadata, and repeat-read pass-through.
- Observe failure fallback, cancellation, and deadlines without running the original reader twice. Include missing/stale sidecars and simultaneous first reads.
- Observe session/new/resume/fork/tree/reload/compaction boundaries, with an explicit session-versus-agent ownership rule.
- In Pi, confirm which tool names actually execute with conversion enabled, then observe override success, fallback, nested calls, and competing extensions in that route.
- For any later attachment proposal, observe each input surface separately and check both model payload and file-I/O timing. A hidden transcript row is not evidence of context removal.

These are proposed proof obligations, not tests or experiments performed by this research.
